### 2.1 Plano e análise de trade-offs

**Problem:** definir a semântica de "taggear todos os módulos" num repositório multi-módulo em que cada módulo tem versão independente (não lockstep).
**Solution:** os contrapontos levantados foram:
- conflito de nome de `-a` com `latest -a` e `git tag -a`;
- módulos dependentes taggeados no mesmo commit;
- flags sem sentido em lote;
- política de erro.

Dois pontos da primeira versão do plano foram retirados depois de questionados pelo usuário:
- a alternativa "pipeline `modules -o json | jq | xargs tag -g`", que perdia em tudo e pulava em silêncio módulos com erro;
- a recomendação de "taggear tudo e avisar", trocada por "segurar" (ver §4).

**Files:** n/a (discussão)

### 2.2 `bumpit tag --all-modules` / `-M`

**Problem:** taggear em lote cada módulo com release, cada um na sua própria próxima versão.
**Solution:**
- **Fluxo:** `tagAllModules()` valida conflitos (`checkAllModules()`), planeja todos os módulos via `ListModules()` e aborta sem criar tag se algum plano falhar (`planFailures()`, com `errors.Join`). Depois `createModuleTags()` cria as tags em ordem (root primeiro) e `writeOutcomes()` imprime uma linha por módulo: `created tag X`, `no release` ou `held: <motivo>; <conselho>`.
- **Exit code:** 1 quando nenhuma tag é criada.
- **Falha do git no meio:** para e devolve o erro, sem rollback. Rodar de novo converge.
- **`holdAdvice()`:** escolhe entre três conselhos: `update <dir>/go.mod, commit and rerun`, `waits for <path>, held too` ou `a requirement cycle: release one of its modules with --module`.

**Files:** `internal/app/tag_command.go`, `internal/app/command_flags.go` (`bindAllModulesFlag()`, campo `allModules`, `checkAllModules()`)

### 2.3 Regra de retenção ("hold") em `ListModules`

**Problem:** taggear no mesmo commit um módulo que requer outro módulo do repositório numa versão antiga publica uma release que requer a versão velha.
**Solution:**
- **A regra:** `holdReleases()` segura todo módulo com release que requer um irmão abaixo da versão mais nova desse irmão. A versão mais nova é o `next`, se o irmão sai nesta execução, ou a tag atual, se não sai (`ReleasePlan.newestVersion()`). Usar a tag atual fecha o buraco da segunda rodada sem guardar estado.
- **Funções:** `outdatedRequirements()` monta a lista, `waitsOnItself()` detecta ciclos e `requiresBelow()` foi extraída e passou a ser usada também por `dependentsBelow()`. Placeholder `v0.0.0-00010101000000-000000000000` não é SemVer válido, conta como abaixo e é segurado.
- **Novos tipos:** `Hold` e `OutdatedRequirement`; `ModuleRelease.Hold` aparece como `hold` no JSON.
- **Exibição e `StartVersion`:** `bumpit modules` mostra `<next>, held: <motivo>` na coluna NEXT via `holdReason()`. `ListModules()` passou a repassar `opts.StartVersion`.

**Files:** `internal/app/go_module.go`, `internal/app/modules_command.go`

## 4. Decisions Made

| Decision | Choice | Alternative Rejected | Evidence | Rationale |
|----------|--------|---------------------|----------|-----------|
| Nome da flag | `--all-modules` / `-M` | `--all` / `-a`, pedido inicialmente pelo usuário | `latest -a` em `command_flags.go`; README: "a letter always means the same thing across commands" | `-a` já significa "todas as tags" em `latest` e "annotated" em `git tag`; o projeto já moveu `--match` para `-t` para preservar `-m` do git. Usuário aceitou |
| Módulos dependentes no mesmo lote | segurar o dependente (b) | taggear tudo e avisar (a) | n/a (usuário questionou e a reavaliação mostrou o furo) | custo assimétrico: um falso positivo de (b) custa um comando; um aviso ignorado em (a) vira versão quebrada permanente após o push. O argumento original a favor de (a) comparava (b) com a proteção perfeita, e não com (a) |
| Referência da regra de retenção | versão mais nova do irmão: `next` se sai na execução, senão a tag atual | comparar só com o `next` de irmãos que saem na mesma execução | cenário "second run" nos testes | sem estado entre execuções, a regra fraca deixaria a segunda rodada taggear sem atualizar o `go.mod`. Custo aceito: quem fixa de propósito um irmão antigo só sai por `--module` |
| Política de erro | planejar todos antes; se algum falhar, nenhuma tag | taggear os que deram certo, como o `modules` lista erros e segue | n/a (usuário escolheu) | escrita parcial com erro escondido é como releases se perdem; a saída é `--module` |
| Flags no lote | recusar `--module`, `--match`, `--release-as`, `--pre`, `--promote` (inclusive vindas do config, com mensagem citando a chave); aceitar `--start-version` e `-m` / `tagMessage` | aceitar `--pre` / `--promote` com regra de pular | `explicitPreRelease()` em `release.go` incrementa `beta.N` sem commits | `--pre` subiria todo módulo em beta sem mudança; restringir agora e abrir depois é retrocompatível; mantém a convergência ao rodar de novo |
| Exit code | falha só quando nenhuma tag é criada | falhar quando há qualquer módulo segurado | n/a | segurar é passo previsto do fluxo, não falha; mesma regra do `tag` atual |
| Falha do git durante a criação | parar, reportar o que foi criado, sem rollback | rollback com `git tag -d` | cenário "interrupted" do roteiro isolado | rodar de novo converge: módulos já taggeados ficam sem release |
| Alternativa via shell pipeline | descartada | `modules -o json \| jq \| xargs tag -g` | `ModuleRelease` com `error` tem `has_release: false` | dominada: pularia em silêncio módulos com erro, exige `jq` e o filtro certo |
| Prévia no `modules` | mostrar `held` na coluna NEXT e `hold` no JSON | deixar fora do escopo | n/a | sem isso, a prévia contradiria a ação do `tag --all-modules` |
| Texto do motivo | `requires P V, below N` + conselho por caso | "which is N now" | n/a | quando o requerido também está segurado, N não tem tag, e "now" seria falso |
| Divisão dos commits | feat (código + testes, incluindo o held do `modules`), docs (README), chore (`.claude/settings.json`) | separar o hold do `modules` num commit próprio | `Long` do `modules` cita `bumpit tag --all-modules` | o commit isolado citaria uma flag inexistente; README separado segue o padrão do histórico |
